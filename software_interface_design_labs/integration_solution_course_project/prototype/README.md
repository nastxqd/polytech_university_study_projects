# Прототип интеграции интернет-магазина

Демонстрационный стенд на Python 3.10+ без сторонних библиотек. Он принимает заказ через REST/JSON, проверяет и резервирует остатки в SQLite, вызывает имитацию платёжного шлюза, а подтверждённый заказ передаёт CRM-консьюмеру через транзакционный outbox. Успешные заказы синхронно проводятся через локальный обработчик, чтобы сценарий можно было показать без брокера и внешней инфраструктуры.

## Запуск

```powershell
python app.py
```

Сервис слушает `http://127.0.0.1:8080`. База `integration.db` создаётся рядом с приложением. Для отдельного файла задайте переменную окружения `INTEGRATION_DB`.

## Пример

```powershell
Invoke-RestMethod -Method Post -Uri http://127.0.0.1:8080/orders -Headers @{ 'Idempotency-Key'='demo-order-001' } -ContentType 'application/json' -Body '{"customerId":"C-100","items":[{"sku":"SKU-LAMP","quantity":2}],"paymentApproved":true}'
```

Отказ платежа воспроизводится значением `paymentApproved:false`. Повтор того же запроса с тем же `Idempotency-Key` возвращает уже созданный результат. Доступные артикулы и цены заданы в `app.py`.

## Маршруты

| Метод | Путь | Назначение |
| --- | --- | --- |
| GET | `/health` | Проверка доступности |
| POST | `/orders` | Создание и сквозная обработка заказа |
| GET | `/orders/{id}` | Чтение заказа и позиций |

Контракты событий приведены в `contracts/`. Прототип хранит денежные суммы в копейках, включает защиту от повторного HTTP-запроса, транзакционное списание остатков и дедупликацию CRM-событий. Ошибки возвращаются в формате `{ "error": { "code", "message", "details" } }`.

## Проверки

Запуск из каталога `prototype`:

```powershell
python -m unittest -v
```

Проверено 7 автоматизированных сценариев: четыре ветки бизнес-логики и три HTTP/JSON проверки. HTTP-проверки подтверждают создание и чтение заказа, повтор с тем же ключом, передачу суммы и позиций, структурированную ошибку при дефиците и восстановление остатка при отказе оплаты. Все 7 тестов завершились со статусом `OK`.

Набор не измеряет производительность, конкурентную нагрузку или безопасность. Тестовый HTTP-сервер использует loopback-интерфейс и временную SQLite-базу.

## Границы модели

`paymentApproved` заменяет реальный платёжный шлюз и предназначен только для демонстрации. SQLite и локальный обработчик заменяют брокер сообщений, а таблица `crm_customers` имитирует CRM. В промышленной версии нужны внешний брокер, секреты и TLS, контроль доступа, отдельные адаптеры, мониторинг, резервное копирование, политика хранения персональных данных и согласование форматов с владельцами систем. Событие из outbox читается атомарно в пределах одного локального процесса; промышленный брокер требует подтверждений доставки и повторов.
